# 有給直接登録の再送・二重消化防止

## 本番適用順序

1. 既存基盤 `application_management.sql` と `leave_manager_balance_permissions.sql` が適用済みであることを確認。
2. `add_admin_paid_leave_usage.sql` が適用済みであることを確認。
3. `add_admin_paid_leave_usage_edit.sql` をレビュー・適用。
4. **最後に** `fix_admin_paid_leave_usage_request_identity.sql` をレビュー・適用。

適用済みSQLの再実行は不要。後から古い `add_admin_paid_leave_usage.sql` を再実行すると登録RPCを旧版に戻すため、修正migrationを最後にする。本番への自動適用はしない。UIの変更・配信は不要。

## 方式

既存キー `admin_paid_usage:使用日:UUID` の末尾UUIDは、編集RPCが使用日・年度を変更しても保持する。新しい登録RPCはこのUUIDで全年度・全社員・削除済みを含め検索する。別社員への同じUUIDの使用は拒否する。

同じ社員でUUIDが既に存在すれば、その履歴が現在所属する年度の残数行を返すだけで、再登録・編集の上書き・削除解除・監査追加・再計算はしない。使用日や日数などが異なる有効なpayloadを再送しても、UUIDを同じ要求として扱い、payloadは適用しない。編集は編集RPC、新規登録は新しいUUIDを使う。これは旧RPCの「同一キーで日数・備考が違えばエラー」からの意図的な変更。

UUID単位のadvisory lock、既存編集削除RPCと同じ社員全年度の残数行のID順ロック、およびUUIDの一意部分インデックスで二重登録を防ぐ。一意制約は `active=false` の論理削除行も含み、通常申請・監査・他種別は除外する。

既存の編集削除RPC・再計算関数は変更しない。使用日を履歴表示する現行キー形式、年度変更、日数変更、残数不足拒否、論理削除と復元、監査方式は維持する。

## 過去データ・事前確認

新しい列・別の要求管理テーブル・データの書換えは不要。既存キーからUUIDを読み取れるため、移行前に編集・年度移動・削除された行もそのまま保護する。

migrationは同じUUIDの複数行（別年度・別社員・削除済みも含む）または不正なキー形式を検出すると、何も自動修正せず全体をロールバックする。既に二重登録が起きている場合は対象社員・日数・残数・監査を確認して別途解決する。行の自動削除・統合は行わない。

一意インデックス作成時にトランザクションテーブルの書込をロックする。実データ件数・作業時間帯を確認して適用する。実環境のRPC定義・既存キー形式・権限がリポジトリと一致することも事前確認する。

## 検証

`PGLITE_MODULE` にPGlite `dist/index.js` を指定して以下を実行する。

- `node tests/admin-paid-usage-request-identity-db.test.mjs`: 過去データ保持、重複・不正キーによる適用中止、再適用、日付／日数／年度変更後・削除後の再送、異なるpayload・社員、残数復元、監査・権限。
- `node tests/admin-paid-usage-edit-db.test.mjs`: 新migrationを含む既存編集削除回帰。

同時実行の実サーバー負荷テストは別途実施する。隔離DBではUUID一意制約と各状態の再送・ロールバックを検証する。
