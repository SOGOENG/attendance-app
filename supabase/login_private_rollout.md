# 社員IDログイン（ローカル実装・本番未反映）

## 変更と互換性

- `login.html` の氏名プルダウンを社員ID入力へ変更。社員一覧を読み込まず、初期表示のAuth/REST/RPCリクエストは0件。
- `login.js` は入力IDを正規化して従来と同じ `employee-{id}@staff-portal.local` を端末内で組み立て、既存Authのpassword grantへ送る。IDからメールを問い合わせるAPIや、新しいAuthアカウントは作らない。
- 認証成功後だけ、発行されたJWTを付けて `employees` をAuth IDで絞って取得する。列は既存ログインで使う7列だけ。1件だけであること、入力社員IDとの一致、Auth IDの一致、active=trueを確認してからセッションを保存する。欠損・重複・停止・不一致・SELECT拒否はすべて失敗。
- `portalLoginUser` と `portalAuthSession` の既存形式、`home.html` 遷移、全体/部署/一般/休暇管理権限の保存、共通トークン更新処理は維持。保存した権限は既存画面との互換用で、DB/Edgeの認可の代用にはしない。
- アカウント、パスワード、社員データ、SQL、Edgeは変更しない。新登録Edgeも同じ内部メール形式なので、登録完了後は同じ方法でログイン可能。登録途中のAuth隔離を解除する機能はない。
- 社員IDは既存画面同様JSの安全な整数範囲。全角数字、先頭0、前後空白を正規化する。元の氏名選択に依存していた社員には社員IDを個別に案内する。社員一覧の公開で案内しない。

## 列挙・総当たりへの対策と限界

- 社員の存在・停止・未確認メール・Auth拒否・取得失敗・通信失敗で同一の画面メッセージを表示。Authの応答本文を表示・console出力しない。存在確認API、登録・OTP・パスワード回復APIは呼ばない。
- 実行中フラグとフォーム無効化で重複送信を防ぐ。通信は20秒で中断し、失敗時はセッションを保存せず、認証後の失敗では新セッションのlocal logoutを試みる。既存の他端末セッションを一括ログアウトしない。初期/失敗ログインのパスワードを保存しない。
- クライアントの二重送信防止は攻撃者の制限にはならない。内部メール形式・社員IDは秘密情報ではなく、隠しても総当たり対策にはならない。直接Authへアクセスする攻撃はSupabase側で制限する。
- 本番のAuth rate limitsを確認し、実際の拠点共有IPで正規のログインが妨げられない値に設定・試験する。429を含む失敗時の自動再送はしない。異常な試行回数を監視する。
- CAPTCHAを本番で有効化する場合は、先にサイトキー・許可ドメイン・画面widgetとcaptcha token送信を実装/試験する必要がある。本変更には未設定のCAPTCHAを追加していないため、Dashboardのトグルだけ先行するとログインが失敗する。
- UIのエラー統一はAuthサーバーの生のHTTP応答や処理時間を一定にする保証ではない。隔離環境で不存在/誤パスワード/停止/未確認についてAPI応答とタイミングも確認する。識別可能な差がある場合は、Auth設定・バージョンを確認し、必要なサーバー側対策を別レビューする。DB/Edgeの認可をクライアントで代替しない。

参考：[Supabase Auth rate limits](https://supabase.com/docs/guides/auth/rate-limits)、[CAPTCHA](https://supabase.com/docs/guides/auth/auth-captcha)。本番設定は今回変更・検証していない。

## 本番切替で必要な作業（今回は実行しない）

1. 現在の本番監査では35件の既存Authメール形式が一致。不変のアカウントで動く前提は確認できているが、隔離環境と承認済みの本人操作で、実Auth・権限・Windows/iPhone/iPad実機の最終確認を行う。パスワードを監査用に収集しない。
2. 本人情報7列のauthenticated SELECTを維持する。今回の本人フィルターはDBの閲覧制御の代わりではない。authenticated全員の閲覧範囲を絞る場合は、社員管理・申請・自己プロフィール等の依存を調べ、適切なRLS/閲覧RPCを別途設計する。
3. SQL/Edgeの登録切替とは分けて、互換性のある本ログイン画面を先に配信可能。別途承認されたmain反映で `login.html`、`login.js?v=5`、`login.css?v=1` を揃え、古いタブ・キャッシュ・ホーム画面追加アプリも更新し、実配信ファイルを確認する。旧画面を残したままanon SELECTを撤回しない。
4. 新画面が動くことを確認してから、`restrict_employee_anonymous_reads.sql` でanonのemployees SELECTを遮断する。適用担当者はレビュー済み配信SHAを `portal.reviewed_login_revision`、実Auth確認を `portal.id_login_verified=yes` として同じセッションで明示する。PUBLIC由来・列ACLを撤回し、継承によるSELECT残存やauthenticated/service_role SELECTへの影響はトランザクション全体を停止する。publicビュー/RPC・公開schemaの迂回経路も確認する。authenticated SELECTを同時に撤回しない。
5. 匿名取得が拒否されても新ログインが成功し、一般/部署/全体管理者の画面と正規権限が維持されることを確認する。直接書き込み遮断・登録ゲートは社員管理全体の協調切替手順に従う。
6. バックアップ・配信リビジョン・旧権限を記録する。障害時は新画面/認証後SELECTを修正し、匿名の全社員公開を戻すことを通常の復旧策にしない。

## ローカル検証

`tests/login-private-ui.test.mjs` はローカルHTTPサーバーとブラウザーを使い、Supabaseへの通信をすべてモックに置き換える。匿名SELECTは禁止するモックで、認証前の通信0件、JWT付きの本人照会、取得後だけの保存を確認する。

- 全体/部署/一般/休暇管理権限の引継ぎ、既存セッション形式、Enter、全角/先頭0付きID。
- 15種類の認証/通信/本人検証失敗で同一メッセージ、セッション非保存、パスワード非保存、認証後拒否時のlocal logout。
- 不正/注入文字/安全な整数範囲外のID、重複送信、1440/768/390/320pxでのはみ出し・44px以上の操作領域。
- 実サービス・実社員・実パスワードへのアクセスは行わない。画面幅の確認は実iPhone/iPad Safariの実機試験と区別する。

実行結果：Windows Chrome・Edgeで各5群成功。両ブラウザーで1440/768/390/320pxの検証と画像保存を完了。JavaScript構文と `git diff --check` も成功。実Auth・実機Safari・本番権限撤回は未実施。
