# 給油領収書：本番適用直前の確認と停止・復旧

2026-10-17。ローカルコードの静的確認。本番接続・SQL適用・Edge公開は未実施。
手動バックアップは認証失敗のため取得できていない。ユーザー判断によりバックアップとテスト用Supabase作成を見送る。

## SQLの影響と失敗時

- 新規5テーブル、関数、インデックス、RLS、非公開バケット、Storage制限ポリシーを追加する。
- 既存日報にBEFORE UPDATEトリガー、既存給油にBEFORE DELETEトリガーを追加する。既存テーブル列・提出RPC・既存RLS・既存行の一括変更はない。
- 全文のBEGINからCOMMITまでを同じセッションで一括実行する。途中のSQLエラーはトランザクションを失敗状態にし、同トランザクションのDDL・バケット行・ポリシーもロールバックされる。途中だけ実行しない。接続を残した場合はROLLBACKして失敗トランザクションを終了する。
- COMMIT直後の切断では、クライアントに結果が届かなくても確定済みの場合がある。オブジェクト存在を確認するまで再実行しない。既存オブジェクトとの衝突も失敗する仕様で、再実行可能migrationではない。
- CREATE TRIGGER/FK作成時のテーブルロックは業務の保存を一時的に待たせ得る。利用の少ない時間帯に短時間で全文適用する。長いロック待ちは中断して結果確認する。

## 保存・提出と段階公開

- 給油保存は既存IDをPATCHし、追加だけINSERT、削除指定行だけDELETE。添付のない給油の削除は従来どおり。
- 添付のactive/pending/deletingがある給油の削除を拒否する。pending/deletingを持つ日報の提出を拒否する。障害時にも保護を維持するための意図した制約である。
- SQLだけ適用し、領収書が空かつ旧画面のままなら、上記条件に該当せず通常運用できる。新規バケットは空である。
- 新画面は給油削除の前にEdgeへ照会する。Edge未公開・停止中は給油削除が失敗する。添付欄にも読込エラーが出る。SQLだけで新画面を公開可能になったとは扱わない。
- 公開順序はSQL→Edge→動作確認→画面。画面の関連JS/CSS/管理ナビも一式で管理する。

## Storage・認可の条件

- fuel-receiptsは非公開、8MiB/件、JPEG/PNG/PDF。anon/authenticatedへのrestrictive policyが専用バケットの直接操作を拒否する。他バケットへの既存の許可は追加しない。
- 既存の許可ポリシーが0件でも、Edgeのservice_roleは標準のStorage ACLとBYPASSRLSにより操作する。既存の広い許可ポリシーがあっても専用制限が適用される。
- メタデータは本人/経理のRLS、書込はservice_roleだけが実行できるRPC。EdgeはJWT検証後の社員UUIDを渡し、SQLが有効社員・本人下書き・経理/全体管理者を再検証する。
- 本番の関数所有者、Storage ACL、ロール、既存ポリシーはローカルと同じとは保証できない。fuel_receipts_preflight.sqlによる読取確認が必要。匿名・他社員の拒否と本人/経理の操作は実環境で確認する。

## データを消さずに停止する

1. 社員へ利用停止を案内し、実行中のアップロード・削除・ZIP処理を終了させる。管理ナビと新規添付操作を公開停止する。
2. DB ownerが必要時に次のSQLでRPCの新規呼出しを止める（準備例のみ、未実行）。

```sql
begin;
revoke execute on function public.fuel_receipt_command(uuid,text,jsonb) from service_role;
commit;
```

3. Edge公開を停止し、給油行IDを維持して保存する領収書導入直前の画面一式へ戻す。無関係の作業を含むgit resetで戻さない。導入前画面のファイル一式を公開前に確保する。
4. バケット・テーブル・監査・RLS・保護トリガーは残す。DROP/CASCADE、Storageバケット削除、提出保護解除は行わない。

REVOKEは進行中のRPCやStorage操作を取り消さない。発行済み署名URLは最大60秒残り得る。メタデータの正当な本人/経理のSELECTは引き続き可能。完全なアクセス停止ではなく、追加機能の新規操作を止める手順である。

再開時は原因を解消した上で、同関数へのEXECUTEをservice_roleへ再付与し、Edgeと画面をそろえて再開する。停止・再開のSQLも本番実行には別途承認が必要。

## 元の運用へ戻す限界

- 添付未利用なら追加オブジェクトを残して旧画面へ戻すことで通常の保存・提出を維持できる。
- 添付利用後も通常の給油量/メーター更新は可能。ただしactive添付付き給油の削除やpending/deletingを持つ日報の提出は保護される。完全に以前と同じ操作へ戻るわけではない。
- 処理途中の行は実Storage状態を確認し、Edgeを修復して正規の完了/削除操作で解消する。状態だけactive/removedへ強制更新しない。一般社員は提出後の添付を変更できない。
- 実ファイル削除済みでDB完了だけ失敗した場合、復旧後に再試行できるが、削除した実ファイル自体はSQLロールバックでは戻らない。
- バックアップなしでは誤削除・想定外のデータ破損を導入前の状態へ完全復元する保証はない。適用成功後の変更はROLLBACKでは取り消せず、修復用の別トランザクションが必要。
