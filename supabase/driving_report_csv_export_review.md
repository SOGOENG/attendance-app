## 2. RLS・SELECT権限

### 初版の問題

SECURITY INVOKERでのSELECTは、GRANT不足なら42501になるが、RLSの行除外では正常に0件や部分集合が返る。特にM自体が見えなければJSは「提出0人」、過去給油が見えなければ「履歴なし」と解釈し得る。現在日報の欠落検証だけでは保証できない。

リポジトリ上の日報・明細・月別提出のRLSには全体管理者の読取条件がある。一方employeesの本番RLS/GRANTはリポジトリだけでは全体像が分からず、applications等も実定義との照合が必要。会社用DBでの完全取得を初版のまま保証できない。

### 修正した権限構成（本番採否は実定義照合後）

- 新規RPCだけをSTABLE / SECURITY DEFINER、空search_path、関数内row_security=offとする。
- Auth UID必須、既存is_application_admin()による有効な全体管理者判定を毎回行う。引数は締め月だけで、社員や車両を自由指定する任意SQL入口にはしない。
- 月別提出社員・期間・実日報車両で読取範囲を固定する。SQLは静的SELECTのみ。既存RPCやRLS、テーブルGRANTは変更しない。
- 関数所有者には、各表の必要なSELECTとRLSの影響を受けずに読む能力が必要。通常はレビュー済みpostgres所有を想定するが、本番所有者を未確認のまま保証しない。
- 所有者にSELECTがない場合、またはRLSの影響を受ける場合はエラー。row_security=offは「誰でもRLSを迂回できる権限」ではなく、適用されるRLSがあればエラーにする設定。FORCE RLSや所有権変更も確認する。
- PUBLIC/anon/service_roleのEXECUTEを剥奪し、authenticatedには新RPCのEXECUTEだけを付与する。テーブルSELECT追加、利用者へのBYPASSRLS付与、RLS無効化は行わない。

これは呼出者の既存RLSを使って全件取得する構成から、認可済み管理者に限定して所有者の読取権限を使う構成への変更。新RPCの管理者認可と所有者を本番で確認する必要がある。クライアントはv2と完全取得契約を検査し、権限/RLSエラーを0件として処理しない。

## 3. 前回給油の取得

検索キーは当月正式出力の実日報に保存されたvehicle_id。現在の既定車両や社員IDだけでは検索しない。対象期間開始日のJST 0時より前のrefueled_atを対象にし、別社員・inactive社員による同一車両の履歴も候補に含む。

正式候補は、親日報submitted、対応月別提出あり、snapshot.valid=true/errors=[]、期間が一致し、当該日報ID/日付/required/issueが整合する履歴。日別提出のみ・下書き・月別未提出・月別snapshot不整合は正式候補にしない。

| 状態 | 出力 |
|---|---|
| 最新正式候補が正常 | available |
| 正式履歴も未確定履歴もなし | no_history。給油ID・日付・量・メーターを空欄にする |
| 候補より新しい/同時刻の未確定履歴あり、または未確定履歴だけあり | unconfirmed_history。古い正式候補を無断で実際の最終給油へ確定しない |
| 同時刻の正式候補が複数 | 最大IDは選択規則として保持するがorder_unconfirmed。件数を別列に出す |
| 同日で異なる時刻 | 保存日時順。マイクロ秒を保持。ただし画面は実給油時刻を入力せず0時保存するため、記録された順序の保証に限定 |
| 最新メーターNULL/逆転/日付不一致 | needs_review。古い正常な給油へ差し替えない |
| 月途中車両変更 | 各vehicle_idで独立。別車両のメーター・燃費を混ぜない |

応答は車両ごとに「最新正式候補」「それより前の直前正式候補」の最大2明細と、同時刻件数/未確定有無/選択IDの集約。サーバー内部では過去履歴全体を検査するがブラウザへ全件を返さない。200件の同時刻給油でも返却量は最大2明細の契約を維持する。追加インデックスは今回導入せず、本番履歴量で実行計画/応答時間を確認する。

## 4. 対象社員

リポジトリでは専用のdriving_report_required/driving_required等の対象者フラグ・名簿を確認できない。既存attendance_requiredは出勤簿対象であり、employees.default_vehicle_idは本人が設定できる任意の入力初期値。active、所属、既定車両、過去の日報の有無だけでは「運転日報対象約30人」を確定できない。実DBに別の設定があるかは未確認。

現段階では手動確認を維持する。候補一覧は在籍社員＋当月月別提出社員であり、自動判定の対象名簿とは表示しない。管理者が未提出を含む対象者を選び、提出済み社員は必ず集合に含める。未提出数はその選択名簿−月別提出社員集合、正式出力は月別提出社員集合。集合の和集合を選択名簿として保つため、提出済み人数と正式出力人数は一致する。初期の未提出0人を会社全体の提出完了と表示せず、会社全体の対象人数は名簿確認が必要と明示する。

本番設定の調査で専用名簿が見つかれば、その有効期間・異動/退職の扱いを確認して連携する。ない場合は、既定車両を対象フラグへ読み替えず、正式な名簿管理を別途決める。退職済み未提出者を確認候補に含める必要がある場合もこの決定が必要。

## 6. テスト

純粋CSV試験20群とChrome模擬RPC画面試験9ケースも成功。RLSエラーで人数を0件表示して継続しないこと、旧版RPCを拒否することも確認した。既存業務ロジック自体は今回変更していないが、本番の全既存DDL・Edge/Storage・同時更新・負荷・Excelの検証の代替ではない。
