# 運転日報 月別提出・改善版（本番未適用）

対象SQLは初回適用用の準備ファイル。画面・本番環境・既存データの移行や削除は行わない。前版を適用したローカルDBには再適用せず、新規の隔離DBで検証する。本番への適用は別途承認後。

## API・権限

- `check_driving_report_month(date)`：月初の日付を指定。本人の期間、日別根拠、不備、提出可能日を読み取り確認する。事前確認は予約ではなく提出時に再検証する。
- `submit_driving_report_month(date)`：本人の期間全体を一つのトランザクションで提出する。成功後の再送は同じ月別提出記録を返す。社員IDと現在日時を指定する引数はない。
- 2026-10-01指定 → 9/21〜10/20、日本時間10/21から提出可能。年越し・閏年も同じ計算。
- `driving_report_month_submissions`は本人・全体管理者のSELECTのみ。直接書き込みは禁止。社員・締め月の一意制約を維持する。
- `driving_report_month_gates`は社員・締め月単位の永続ロック行。クライアントには読み書き権限を付与しない。
- 既存提出済み日報と初回提出日時は更新しない。日別提出RPCは残るため、このSQLだけでは日別提出方式は廃止されない。

## 排他制御と実際の更新経路

全体テーブルロックは使用しない。社員・締め月キーのトランザクションadvisory lockで未作成ロック行の生成競合を処理し、その後、永続ロック行をFOR UPDATEする。内部ハッシュの衝突時も保守的な待機・拒否となり、整合性は迂回できない。

| 更新経路 | ロックと処理 |
| --- | --- |
| 月別提出RPC | 社員・締め月ロック → カレンダー共有ロック → 日報行をID順でロック → 再検証 → 日報提出 → 月別記録 |
| 既存日別提出RPC | 同じ月ロックを日報行より先に取得 → 元の処理 |
| 領収書RPC | 対象日報の社員・締め月を確認 → 同じ月ロック → 元のrefuel/report/receipt/quota処理 |
| 日報・点検・アルコール・給油の直接REST更新 | 行トリガーで同じ月ロックを**待たずに**取得。競合時は55P03で中止。取得後に提出状態を再確認 |
| 出勤簿・休日出勤・申請・有給/代休明細の更新 | OLD/NEW両方から影響月を列挙し、一定順序で同じ月ロックを待たずに取得 |
| 休日設定の更新 | 影響する締め月のカレンダーロックを待たずに排他取得 |

直接UPDATE/DELETEの行トリガー時点では、対象行が既にロックされている可能性がある。そのためトリガーで月ロックを待たせない。行ロックを持つ側が`driving_month_busy_retry`でロールバックし、提出側が処理を進める。RPCは行を触る前に待機し、待機後に元の権限・状態確認を実行する。行トリガーだけに依存せず、既存RPCの入口も調整している。

別社員と別締め月の保存は独立する。同じ締め月の別社員による提出も、カレンダー共有ロック同士は競合しない。領収書容量確認の既存グローバルadvisory lockは維持しており、その短時間の競合まで取り除くものではない。

カレンダーと勤務情報の新規追加・削除・日付移動・社員移動・承認・取消も対象とする。月別提出中の変更は55P03で中止する。提出後の出勤簿・休日出勤記録・休日マスタの通常変更は許可し、提出時のスナップショットは変更しない。ただし、今回の確定要件に従い、提出済み期間に関係する申請と有給・代休明細の変更・削除・追加は`driving_month_application_locked`で拒否する。承認・取消・差戻しもその期間に影響する場合は拒否する。未提出期間の既存業務ロジックは変更しない。

標準の1リクエスト1トランザクション・READ COMMITTEDを前提とする。他の分離レベルで月ロックを使う更新は拒否する。任意SQLで複数RPCを逆順に組み合わせる独自トランザクションまで無条件にデッドロックしないと保証するものではない。複数期間の一括操作を将来追加する場合もロック順序と再試行設計が必要。

### RPC互換性と権限

移行内で元の`fuel_receipt_command`と`submit_driving_report`を内部名へ変更し、元の署名にラッパーを設ける。内部関数のPUBLIC/anon/authenticated/service_role実行権限を剥奪する。領収書の入口は従来どおりservice_role限定。日別提出は本人確認を行ってから元の検証を呼ぶ。Edge FunctionのAPIとデプロイは変更しない。

経理の閲覧・原本受領・バックアップ・画像整理・監査は元のコマンドに委譲する。月別提出後の本人による画像変更は元のown_draftチェックでも拒否する。Storage APIやオブジェクトの削除・アップロード自体はこのSQLから実行しない。

## 勤務・休日・休暇

- 「出勤」「有給奨励日」は日報必須。運転なしでも記録する。
- 「休日」「祝日」で休日出勤記録・出勤簿・日報がなければ原則入力不要。曜日だけで免除しない。
- activeの休日出勤記録は日報必須。cancelledは除外。出勤簿が休み・下書き・不明区分などで矛盾する場合は要確認。
- 休日でも本人の日報があれば対象に含める。
- 承認済み全日有給・代休で勤務情報と矛盾しなければ免除。申請から生成されたdraftの休暇行は承認申請・種別・申請IDで照合する。
- 複数日有給は、既存同期と同じく会社休日・祝日を休暇対象日から除く。期間内休日の同期行がないことだけで不備にしない。
- 半日休暇はsubmitted/lockedの勤務、または矛盾のないactive休日出勤が確認できれば日報必須。不明なら要確認。日別対応が曖昧な全日有給やcustom休暇を半日勤務と推測しない。
- 重複、休暇と勤務の矛盾、未確定出勤簿、不明なカレンダーは提出を止める。

下書き日報には既存の正式13点検、車両・メーター・経路、新旧アルコール検査、運転なし明細混在の検証を再利用する。領収書pending/deletingは既存提出済み日報を含めて拒否。未添付自体は新たな必須条件にしない。

提出時の検証結果、日報ID、出勤簿のID・状態・区分・申請ID、全日休暇申請ID、休日出勤IDをスナップショットに保存する。提出済みデータの後日訂正や勤務変更の再確認APIは未実装。既存のlate_entryは日別提出基準のままなので、本番運用前に表示・月別期限との整理が必要。

## 申請連鎖削除の修正

旧ガードは、子明細のDELETE時にもapplicationsを参照していた。親の削除後に起動するON DELETE CASCADEでは社員IDを取得できず、invalid_month_gateで失敗する経路があった。

修正では、親applicationsのBEFORE DELETEで、社員IDと全明細が影響する締め月を取得し、ロックと提出済みチェックを完了してから、`driving_month_application_deletions`に削除証跡を記録する。キーは`pg_current_xact_id()`のxid8＋申請ID。トランザクションIDはクライアントから受け取らない。

子のDELETEで親が見つからない場合は、同じトランザクション・申請IDの証跡から社員と全締め月を取り出し、通常と同じロック・提出済みチェックを再実行する。証跡がなければ`application_cascade_context_required`で拒否する。社員IDがNULLだから許可する分岐はない。直接明細削除では通常どおり生存する親の社員IDを使う。

証跡テーブルはRLS有効、PUBLIC/anon/authenticated/service_roleの権限を剥奪。新しい後処理関数も実行権限を公開しない。セッションGUCやURL値、ローカル保存値は信用しない。

applicationsと各明細テーブルのAFTER DELETE STATEMENTで、親と全3種類の明細が消えた申請の証跡だけを消す。FKトリガーの発火順やSET CONSTRAINTSの状態だけで削除完了を推測しない。複数段の連鎖途中で証跡を消さず、最後の段階で削除する。正常コミット後に証跡を残さず、失敗時には元データと証跡の両方がロールバックされる。

追加検証は、有給/代休それぞれの親直接削除・既存RPC・子直接削除、二段のFK連鎖、複数親一括削除、複数締め月、通常/SET CONSTRAINTS ALL IMMEDIATE、意図的な削除後エラーの全件復元、他社員のRPC拒否、証跡の参照/書込権限、承認同期/取消/差戻し状態、削除先行時の提出待機、提出先行時の削除拒否、提出コミット後の親/子変更・削除拒否を含む。並行操作はREADY通知とpg_stat_activityの待機確認で同期する。

今回の修正による本番適用・既存データの削除は行っていない。取得済み本番定義を用いた追加の統合検証は下記。実環境の負荷・外部ジョブの呼び出し確認は引き続き必要。

## 本番適用前改善：内部同期関数の権限

取得済みの本番カタログでは、`sync_application_attendance_date(bigint,bigint,date,text)`と`sync_approved_application_attendance(bigint)`にanon/authenticated/service_roleの直接EXECUTEが残っていた。リポジトリのPUBLIC剥奪だけでは既存の明示GRANTは取り消せない。前者は呼出者の社員・申請状態を検証する公開RPCではなく内部関数であり、直接公開を避ける。

通常経路は、審査RPC→applications.status更新→`handle_application_attendance_status()`（SECURITY DEFINER）→承認同期→日別同期。ブラウザからの直接呼出しは既存JS/HTML/Edgeコードに見つからない。手動修復用SQLには承認同期の直接呼出例があるため、所有者による保守と、外部ジョブの有無は区別して確認する。

権限是正は独立した`restrict_application_attendance_sync.sql`に分離する。月別提出とは別のセキュリティ変更であり、適用・レビュー対象を明確にするため。両内部関数についてPUBLIC/anon/authenticated/service_roleの権限を剥奪し、所有者の内部実行を残す。適用時にSECURITY DEFINER呼出鎖と同一所有者をチェックし、不一致ならトランザクションを停止する。関数の引数・戻り値・本体・search_path・所有者は変更しない。一般の申請RPCやservice_role専用の代休自動失効RPCの権限は変更しない。

ローカルでは本番の明示GRANTを再現してから是正SQLを適用し、3ロールの実行権限消失、社員からの直接呼出拒否、権限是正後の実審査RPC・トリガー内部同期成功を検証した。リポジトリ外のジョブ・手動運用が内部関数を直接呼んでいるかは未確認。存在する場合は認可された入口へ移す設計が必要で、無制限なEXECUTEを戻さない。

## 本番適用前改善：代休台帳と実際の休暇の分離

管理者直接登録は、`admin_direct=true`の明細と`reviewer_comment`の`admin_comp_usage:`識別子を持つ残高台帳。2.25日などを1日にまとめて記録でき、実際の出勤簿を生成しない。これを全日/半日休暇と解釈すると、勤務日の必要日報を誤って免除するため、事前確認では直接登録明細を休暇判定から除外する。

ガードでは、正規の代休種別・識別子・直接登録明細のみ・同期出勤簿なしを確認した台帳について、既存RPCによる訂正・取消を月別締めから独立させる。社員の付替えや通常休暇への変換を無条件に許可せず、OLD/NEW双方で確認する。非公開判定ヘルパーに一般ロールの実行権限は与えない。通常の有給・代休申請と明細の変更・取消は提出済み期間で引き続き拒否し、失敗した残高変更もトランザクションで復元する。

有給残高の期首訂正・直接使用登録、代休残高の直接登録・訂正・取消・期限失効について、既存関数・台帳・制約を使用する。残高を月別提出の検証スナップショットや勤務実績そのものと混同しない。出勤簿・休日出勤元データの既存の履歴スナップショット方針は変更していない。
